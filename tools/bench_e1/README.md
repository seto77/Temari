# bench_e1 — 実験 E1: プロセス並列 vs スレッド並列の再計測ハーネス

`docs/speedup_audit_2026-08-05.md` P4-1 の再実験。2026-08-04 の実測
「8 プロセス×4 スレッドが 4 プロセス×8 スレッドの 2.26 倍」は Phase 1
(角度融合・割り当て −96 %、d688a35) と P2-1 (e8603a3) より前のもので、
GC 圧が交絡していた疑いがある。現行コードで **単一プロセス多スレッドが
プロセス並列に追いつくか** を公平な条件で測り直し、「GC がスレッド並列を
殺す」仮説の生死を決める。

## 構成 (同一ジョブ表を 4 構成で流す)

| config | プロセス × スレッド | gcthreads |
|---|---|---|
| c1_8p4t | 8 × 4 (現行本番構成) | Julia 既定 |
| c2_1p32t | 1 × 32 | Julia 既定 |
| c3_16p2t | 16 × 2 | Julia 既定 |
| c4_8p4t_gc1 | 8 × 4 | 1 (実験 E3 の相乗り。gcthreads はビット同一に影響しない) |

## 使い方

```powershell
# 煙試験 (数分。配管の検証のみ — 数字に意味はない)
pwsh -File tools\bench_e1\run_e1.ps1 -Smoke

# 本計測 (既定: 6 チャネル × 8 E0 行 = 48 ジョブ、HIGH 設定・S_GRID 161 点)
pwsh -File tools\bench_e1\run_e1.ps1

# 1/4 スケールの下見 / スケール拡大
pwsh -File tools\bench_e1\run_e1.ps1 -Rows 2
pwsh -File tools\bench_e1\run_e1.ps1 -Rows 12
```

主なパラメータ: `-Julia` (既定 `julia`)、`-JuliaChannel` (既定 `+1.11` =
juliaup で本番ピン 1.11.9 を選択。`""` で PATH の julia)、`-MaxCpuPct 20`、
`-ConfigTimeoutMin 180`、`-CooldownSec 45`、`-Force` (アイドル検査スキップ、非推奨)。

新規ファイルは本ディレクトリのみ。既存ファイルは一切変更しない。
結果は `tools\bench_e1\results\e1_<stamp>\` に
`summary.md` + `config_*.json` + `meta.json` + `plan.json` +
`configs\<cfg>\{out,done,logs}\` として残る。

## ⚠ 実行前に必ず読むこと

- **マシンを飽和させる**。全 32 論理コアを長時間 100 % にする。ドライバは
  起動時に既存 CPU 負荷を検査し、`-MaxCpuPct` (既定 20 %) を超えていれば
  拒否する。計測中は他の作業をしないこと。
- **Julia バージョン**: 本番ピンは **1.11.9** (`atom_cache_jl111_*` /
  audit の掟 §0-3)。この環境の PATH の `julia` は **1.12.6** なので、既定で
  `julia +1.11` (juliaup チャネル) を使う。1.12 で走らせると (a) SCF
  キャッシュが jl112 名で別に作られる、(b) Windows の並列 GC segfault
  既知問題 (gen_production.jl 冒頭) を踏み得る、(c) 本番構成判断の材料と
  して弱くなる — ドライバは検出して警告する。
- **GC wedge**: Windows Julia は高負荷でプロセスが死なずに固まることがある
  (src/IMPORT.md)。ドライバは 1 構成 `-ConfigTimeoutMin` (既定 180 分) で
  強制終了し、その構成を FAILED として続行する。

## 所要時間の目安

HIGH 1 行の現行コスト (Phase 1+P2-1 後) は未実測のため幅を持たせる。
経験則で 4 スレッド 1 行 ≈ 0.5–3 分 (Z・E0 依存) とすると、既定 48 ジョブで:

| 項目 | 目安 |
|---|---|
| warmcache (初回、Z=48 の SCF 込み) | 2–6 分 (2 回目以降 ~1 分) |
| c1_8p4t / c3_16p2t / c4_8p4t_gc1 | 各 5–20 分 |
| c2_1p32t | 5–20 分 (32 スレッドのスケールが良い場合)。**スケールが悪いと 30–60 分** — それ自体が E1 の答え |
| **合計** | **およそ 0.5–1.5 時間** (-Rows に比例。`-Rows 2` で ~1/4) |

## ジョブ表 (チャネル選定の理由)

6 チャネル × `-Rows` 本の E0 行。E0 は本番と同一の `e0_grid(z, tag)` から
等間隔インデックスで抽出 (低 u ～ 高 E0 を張る)。

| チャネル | 理由 |
|---|---|
| Z=6 K | 最軽量 K (下限側の代表。SCF キャッシュ既存) |
| Z=26 K | 中量 K (audit の基準ケース。キャッシュ既存) |
| Z=48 K | 重い K。本番で GC クラッシュ修復歴のある Cd-K (キャッシュは warmcache が作る) |
| Z=38 L3 | 中量 L (キャッシュ既存) |
| Z=53 L1 | 2s 動径ノードあり = s≤8 拡張の問題児 (キャッシュ既存) |
| Z=79 L3 | 重量 L (キャッシュ既存) |

軽 Z K ～ 重 Z L を張り、本番 246 チャネルの負荷分布 (行コストの軽重混在)
を小さく代表させる。5/6 チャネルは既存の `atom_cache_jl111_*` をそのまま使う。

## 公平性ノート (プロトコルの設計根拠)

1. **同一の仕事**: 全構成が同じ `plan.json` (同じジョブ集合・同じ順序) を
   消化する。設定は本番と同じ `HIGH_SETTINGS` + `S_GRID` 161 点 +
   SRC (`rel_continuum=true`)。QUICK では割り当て・帯域プロファイルが変わり
   E1 の問い (GC/メモリ挙動) に答えられない。
2. **動的キュー**: ジョブ取得は `claims/<id>` の mkdir (アトミック) による
   早い者勝ち。本番の静的レーン分割 (`--lane i/n` の剰余) だと 8 分割と
   16 分割で不均衡の当たり外れが変わり、並列効率と配分運の区別がつかない。
   E1 は並列効率だけを見たいので配分はキューで均す。ジョブ列は重い見積り順
   (LPT) に並べ、尻尾の待ちを最小化する。
3. **バリア計測**: 各ワーカは include + JIT ウォームアップ 1 行 (HIGH と
   同じ NamedTuple 型の軽量設定 = 同じメソッド特殊化を温める) を済ませてから
   ready を報告し、全員揃ってから go → 最終ワーカ終了までを壁時計で測る。
   起動・コンパイル時間はプロセス数に比例するため、含めると多プロセス構成が
   不当に不利になる (E1 の問いは定常スループット)。参考値として startup_s も残す。
4. **SCF キャッシュの等温性**: キャッシュは CWD 相対 (`cache_file` は相対
   パス) なのでワーカは `cd(src/)` で走り、全構成が同じ `atom_cache_*.jls`
   を共有する。計測前に warmcache が 6 チャネル全ての n/i/d キャッシュを
   1 回だけ作る (束縛側は求積設定に非依存なのでこれで十分)。
5. **本番との一致**: ワーカは本番レーンと同じく BELOW_NORMAL 優先度を自己設定
   (`set_below_normal_priority`)。E0 グリッドも本番の `e0_grid` そのもの。
6. **正しさの機械検証**: F はスレッド数・プロセス数に依存しない設計
   (ionization.jl)。サマリで全ジョブの F の sha256 を構成間比較し、
   不一致があれば exit 3 で赤旗を立てる。
7. **熱・順序**: 構成は直列実行 (c1→c2→c3→c4、間に cooldown 既定 45 s)。
   熱の持ち越しは完全には消えないので、**結論を出す前に順序を変えて
   もう 1 回流す** こと (このハーネスの数字 1 回で採否を決めない)。
8. **計測外のもの**: プロセス起動、include、JIT、SCF ウォーム、結果 JSON の
   読み書き (行計算に比べ微小)。

## 結果の読み方

- 主指標 = `wall_s` (バリア → 最終ワーカ終了)。`summary.md` に
  rows/min と c1 基準の speedup が出る。
- `work_span_s` (ワーカ時刻での最初の行開始 → 最後の行終了) と
  `busy_s_total` (Σ 行時間) で尻尾の不均衡・レーン内効率を診断できる。
- 判定の目安: c2_1p32t の wall が c1_8p4t の ~1.1 倍以内なら「GC がスレッド
  並列を殺す」仮説は死亡 (Phase 1 の割り当て −96 % が原因だったと確定)。
  依然 1.5 倍超なら仮説は生存し、プロセス並列の維持が正当化される。
  c4 と c1 の差は E3 (gcthreads=1 のコスト) の判断材料。
