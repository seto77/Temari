# ホストの安定性 — 全格子認証が BSOD で止まった件と、その周辺 (2026-08-18)

⚠ 本書は**測定と記録**であって、原因の断定ではない。何が観測で何が推論かを分けて書く。

## 1. 起きたこと

`σ(β,Δ)` の全格子認証を **8 レーン × 4 スレッド (= 論理 32 本を使い切る)** で起動した
ところ、**1 行も書けないうちにホストが落ちた**。

| | |
|---|---|
| 起動 | 2026-08-18 14:04:46 – 14:05:00 (8 レーンを 2 s 間隔) |
| 落ちた | 14:05 – 14:10 の間 (全レーンが JIT コンパイル中の時間帯) |
| 復帰 | 14:11:07 (EventLog 6005) |
| 種別 | **BSOD** — bugcheck `0x00000139 (0x3, …)` |
| 損失 | **無し** — JSONL は 8 本とも 0 バイトだった |

`0x139` = KERNEL_SECURITY_CHECK_FAILURE、第 1 引数 `3` = **LIST_ENTRY の破損を検出**。
カーネル側の連結リストが壊れていた、という意味である。

⚠ **電源・熱ではない**。Kernel-Power 41 は出ているが、これは BSOD に必ず伴うもので、
`WER-SystemErrorReporting 1001` が同時刻に bugcheck を記録している。

### 2.1 読み方 — 2 つの筋が両方立つ

**(a) メモリ/プラットフォームの不安定を示す側**

- 種別が**ばらばら**で、しかも `0x4E` PFN_LIST_CORRUPT・`0x139` LIST_ENTRY 破損・
  `0xBE` 読み取り専用への書き込み、と**破損そのもの**を名乗るものが 3 系統ある。
  単一のドライバのバグなら普通はもっと**同じ場所で**落ちる
- `0x101` CLOCK_WATCHDOG_TIMEOUT (コアが割り込みに応答しない) が混ざる。これは
  ドライバのバグでは説明しにくく、CPU/メモリの動作限界側の典型
- **メモリ構成が AM5 の最難構成である** (§3)

**(b) ドライバのバグを示す側**

- `0x1E` 4 件のうち **2 件は第 2 引数の下位が一致する** (`…d8f17680` と `…aeb17680`
  = モジュール内オフセット `b17680`)。ASLR で基底は動くのでこれは
  **同じ関数の同じ行で 2 回落ちた**ことを意味する。ランダムなビット化けでは説明しづらい
- 残り 2 件 (`…eb8b5177`, `…83b644dd`) は別のオフセット

⇒ **どちらか一方に決められない**。少なくとも「同じ場所で 2 回」の分は再現性のある
コード経路であり、`0x4E`/`0x139`/`0x101` の分は動作限界側に見える。
両方が同時に起きていても矛盾しない (不安定なメモリは、脆いドライバを先に殺す)。

## 3. メモリ構成 — AM5 で最も難しい挿し方になっている

```
4 × 32 GB  Kingston KF552C40-32  (DDR5, SPD 4800 表記, CL40)
P0 CHANNEL A: 2 枚 / P0 CHANNEL B: 2 枚     ← 全 4 スロット占有
ConfiguredClockSpeed = 4400 MT/s            ← 既に降ろされている
合計 125.7 GB
```

**AM5 (Ryzen 9 9950X) は 1 チャネルあたり 2 枚 (= 4 スロット全部) にすると
メモリコントローラの余裕が急に無くなる**のがよく知られている。32 GB モジュールは
デュアルランクなので、チャネルあたり 4 ランク = 最も条件が厳しい。
**マザーボードが自動で 4800 → 4400 へ落としている**のは、その難しさの現れである。

⚠ これは**一般に知られた傾向**であって、このホストで測った値ではない。

## 4. ★ Temari にとっての意味 — 「Julia の GC クラッシュ」の説明になりうる

本プロジェクトは長く**原因不明の 2 つの現象**を抱えている。

| 現象 | これまでの記録 |
|---|---|
| **Julia の GC クラッシュ** | v4 生成中に **5 回** (うち 2 回 wedged)、v3 でも発生。`EXCEPTION_ACCESS_VIOLATION` が 1.11 は `sweep_malloced_memory`、1.12 は `gc_mark_objarray`。RAM は 126 GB 中 78 GB 空きで**資源枯渇ではない**。`--gcthreads=1` でも `--heap-size-hint` でも変わらない。自コードに `@threads` のデータ競合は無い |
| **SCF がプロセス間で散発的に別反復で止まる** | 認証 vs 出荷で 34/86、run 1 vs 2 で 6/85、**同順序の 2 プロセスでも**。差は停止許容内。`CLAUDE.md` は「Windows Julia GC 起因のメモリ破損と同根が候補」と書いている |

**カーネルが月に 10 回、メモリ破損系の bugcheck で落ちるホストでは、
ユーザ空間のビット化けも起きていると考えるのが自然である**。そして GC は
「巨大なオブジェクトグラフを全部歩く」処理なので、**プロセス中で最もビット化けに
敏感な部分**にあたる。ポインタが 1 ビット化ければ `sweep_malloced_memory` の中で
アクセス違反になる。浮動小数点が 1 ビット化ければ SCF の収束経路が変わる。

⚠⚠ **これは仮説であって、証明ではない**。否定材料も挙げておく:

- Julia の GC クラッシュは**この 1 台でしか観測していない**ので、
  「処理系の問題ではない」ことを他機と比べて示したわけではない
- Julia 1.11 と 1.12 で**落ちる関数が違う**。純粋なランダムビット化けなら
  もっと散る (ただし GC が最も長く滞在する関数に集中するのは自然でもある)
- SCF の非決定性は**キャッシュ・スレッド数・OS のスケジューリング**でも起こりうる。
  ビット化けだけが候補ではない
- 逆向きの検算がまだ無い — **同じ計算を 2 回走らせてビット比較する常設の検査**が
  あれば、化けを直接数えられる

### 4.1 これが正しいと何が変わるか

- **出荷データの信頼性の議論が変わる**。現在の運用 (「完走 ≠ 健全、QC を必ず通す」・
  行チェックポイント・`is_sane_row` ゲート・C11 の桁外れ検出) は、まさに
  **散発的なビット化けに対する防御として設計されている**ので、対処としては既に正しい。
  変わるのは**原因の帰属**であって、手当ではない
- **「Julia が悪い」という判断を止められる**。言語選定 (2026-08-05 に Julia 続投で決着)
  の再考トリガーに GC クラッシュを含めているなら、**それは根拠として弱い**ことになる
- ⚠ **過去の出荷データを疑う理由にはならない** — v3/v5 は QC を全数通しており、
  v4 の破損 3 行は C11 が捕まえて修復済み。**検査は実際に効いている**

## 5. 取った手当 (2026-08-18)

**負荷を下げてフリートを組み直した** (`tools/run_cert_fleet.sh` の既定を変更):

| | 落ちた設定 | 変更後 |
|---|---|---|
| レーン × スレッド | 8 × 4 = **32 本** (論理を使い切る) | **4 × 3 = 12 本** (論理の 37 %) |
| 起動間隔 | 2 s | **90 s** |
| 優先度 | 既定 | `nice -n 10` |

起動間隔を空けたのは、**落ちたのが全レーン同時 JIT コンパイル中**だったため。
Julia の JIT は最も割り当てが激しい局面で、8 本同時に走らせるのが急性の引き金に見える。

⚠ **これは緩和であって、修理ではない。**§2.2 の切り分けは別途必要。

### 5.1 副作用 — 遅くはならなかった

実測 (2026-08-18 14:15–14:20、lane 0):

```
12 行 / 283 s ≒ 23.6 s/行 (起動と JIT を含む)  → 定常はおよそ 17 s/行
4 レーン並列 ⇒ 実効 4.3 s/行 ⇒ 14,796 行で **およそ 17.5 時間**
```

指示書の見積り (単一プロセス 32 スレッドで **41 時間**) より**速い**。
理由は、既定の窓が **GL 16 点しか無い**こと — 32 スレッドで回すと半分が遊ぶ。
1 行あたりのノード評価は 16 窓 × (16 + 48) = **1024 で固定**なので、
**細かいプロセスに割った方が理想に近づく**。

⚠ **17.5 時間はまだ外挿である**。確定値は完走後の実測で置き換えること。
