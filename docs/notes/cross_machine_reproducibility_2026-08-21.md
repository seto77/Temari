# CPU を跨いだ再現性 — ビット同一は成立しない。判定は丸め誤差の範囲内で行う (2026-08-21)

**結論**: 同じ commit・同じ Julia・同じ設定でも、**CPU が違えば出力バイトは違う**。実測で **7 種類**の
異なるバイト列が出た。差は**すべて最終ビット**で、出荷される F(s) の**最大絶対差 4.441e-16**
(F(0)=1 に規格化した値に対して)。⇒ **データセットの保証を「バイト同一」から「丸め誤差の範囲内で一致」へ
変更した** (作者決定)。

> **保証文**: 同一の commit・同一の承認 spec のもとで、**CPU 世代・ベンダー・命令セットの異なる計算機で
> 再計算しても、出荷される F(s) は絶対 5e-16 以内で一致する**。
> 実測: 実機 9 台 (Zen 5 / Zen 4 / Zen 1 / Skylake-X / Skylake / Coffee Lake、AMD と Intel)、
> 相異なるバイト列 5 種、K 殻の総当たり 10 組すべて合格。M 殻でも最大絶対差 2.220e-16。
> 既知の最小の物理的不確かさ (ε ノード 3.1e-07) より **9 桁小さい**。

判定の道具 = **`tools/agreement_check.py`**。

---

## 0. なぜ変えたか (作者の判断、2026-08-21)

> Temari はオープンソースで、**誰でも出力値を検証できる**のが狙い。AVX2 か AVX-512 かで 1e-15 の差が出るのは
> 読者も納得して無視するはず。いまのままだと **AMD CPU でのみ成立するデータセット**になっている。将来 AMD が
> 新しい CPU を出して計算結果が変わったら最悪。**ビット一致に厳密にこだわらず、1e-15 の違いは無視して設計する。**

この判断は測定に裏打ちされている (§2)。**同値類は CPU 世代ごとに増える**ので、バイト同一を保証にすると
**新しい CPU が出るたびにデータセットが「再現不能」になる**。

## 1. 測り方

- 課題 = **出荷済みチャネル `F_K_Z6` (C の K 殻、22 行、数値 7,370 個) を再計算し、SHA-256 を比べる**。
  出荷経路そのもの (`gen_production.jl --tags K --lane 0/45 --profile v6_high`) を通す。
- コードは NAS 上の内容アドレス tar.gz を**展開前に SHA-256 で検証**してから使う (全機で同一バイト)。
- 基準 = F v6 フリート (Ryzen 9 9950X) が作った `F_K_Z6.json` = `08075e6dd0f120ef…` (174,616 bytes)。
- 道具 = `\\10.31.108.5\jobq\bitcheck.cmd` (ダブルクリック 1 回、管理者権限不要)。実機 9 台 + 同一ホスト上の
  ターゲット指定 5 通り。

## 2. 実測 — 同じコードから 7 種類のバイト列

| # | SHA-256 (先頭 16) | 出どころ |
| --- | --- | --- |
| 1 | `08075e6dd0f120ef` / `7ae0cf24ffc41971` | **Zen 5 native × 2 台** (9950X, HX 370)、**Zen 4 native × 2 台** (7840HS, 7640HS)、`-C znver4` (9950X 上) |
| 2 | `2824e051477f1ded` | **Zen 1 native** (Ryzen 7 2700X) |
| 3 | `2c9d1996e5524ab4` | **Skylake-X native** (Core i9-9960X) |
| 4 | `bd93645cfa0d2bbc` | **Intel × `-C x86-64-v3`** (i7-8700T / i7-6700 / i7-8750H の **3 台が一致**) |
| 5 | `e073f2ab99cc65aa` | **Zen 1 × `-C x86-64-v3`** (2700X) |
| 6 | `54dc97915639787a` | `-C skylake` と `-C skylake-avx512` (9950X 上) |
| 7 | `76b5cfadac0f77a5` | `-C x86-64-v3` (9950X 上) |

★ 類 4 は **Intel の Skylake 系 3 台が互いに一致**している。⇒ 「同じターゲットを指定しても揃わない」のは
機械が違えば必ず、という意味ではなく、**ホストが選ぶ sysimage の版が同じなら揃う**ということ。
だが**どの機がどの版を選ぶかは事前には分からない** (Zen 1 は同じ `-C x86-64-v3` でも Intel 勢と別の値 = 類 5)。

⚠ 1 と 7ae0cf24 の違いは `generator_commit` の 1 フィールドだけ (`.git` を含まないアーカイブから走らせると
`unknown` になる)。**物理量は完全に同一**なので同じ類として扱う。→ この件は §5 で解決済み。

## 3. 差の大きさ — 絶対差で見る

### 3.1 ★ 実機 9 台の総当たり (K 殻、F_K_Z6、数値 7,370 個)

回収した 10 実行 → 相異なるバイト列 5 種。その代表どうしを総当たりで比較した (10 組):

| A | B | 最大相対差 | 最大絶対差 |
| --- | --- | --- | --- |
| Zen 1 native | Skylake-X native | 2.419e-15 | 3.331e-16 |
| **Zen 1 native** | **Zen 4/5 native** | **2.688e-15** | **4.441e-16** ← 最悪 |
| Zen 1 native | Intel×common | 5.324e-16 | 5.551e-17 |
| Zen 1 native | Zen 1×common | 5.324e-16 | 5.551e-17 |
| Skylake-X native | Zen 4/5 native | 1.185e-15 | 3.331e-16 |
| Skylake-X native | Intel×common | 2.316e-15 | 3.331e-16 |
| Skylake-X native | Zen 1×common | 2.316e-15 | 3.331e-16 |
| Zen 4/5 native | Intel×common | 2.613e-15 | 4.441e-16 |
| Zen 4/5 native | Zen 1×common | 2.613e-15 | 4.441e-16 |
| **Intel×common** | **Zen 1×common** | **0.000e+00** | **0.000e+00** |

**10 組すべて合格**。最悪はアーキテクチャが最も離れた **Zen 1 vs Zen 5** の組。

★ **Zen 4/5 native の 4 台 (9950X / HX 370 / 7840HS / 7640HS) はバイト単位で完全一致**した
(同一の 174,616 バイト)。「機械が違えば必ず違う」のではなく、**世代が近ければ完全に一致する**。

★ 最後の行に注目 — **共通ターゲットを指定した Intel 3 台と AMD Zen 1 は、物理量が完全に同一**だった
(SHA-256 が違ったのは `generator_commit` などのメタデータのみ)。⇒ **`-C x86-64-v3` は物理量レベルでは
実際に統一していた**。バイト一致しなかったのは来歴フィールドのせい。

### 3.2 ★ M 殻では相対差が跳ねる — 判定は絶対差で行う

M5 Z=33 を A 類 (native) と B 類 (`-C skylake`) で計算した:

| 指標 | K 殻 (F_K_Z6) | **M 殻 (F_M5_Z33)** |
| --- | --- | --- |
| 最大相対差 | 1.185e-15 | **3.613e-12** |
| **最大絶対差** | 3.331e-16 | **2.220e-16** ← むしろ小さい |

相対差が大きい箇所は**すべて F(s) がゼロを横切る近傍**:

| 箇所 | F の値 | 絶対差 | 相対差 |
| --- | --- | --- | --- |
| `rows[2].F[132]` | −1.5e-11 | **5.4e-23** | 3.613e-12 |
| `rows[8].F[303]` | −2.0e-12 | 5.1e-24 | 2.499e-12 |
| `rows[3].F[155]` | 2.7e-11 | 2.4e-23 | 8.755e-13 |

⚠ **F(s) は F(0)=1 に規格化されており、M 殻では符号を変える** (出荷 v5 で 525 中 358 チャネルが負値を持つ)。
**符号が変わる点で相対誤差は必ず発散する**ので、相対許容差だけを判定基準にするのは物理的に誤り。

⇒ 判定式は **`|a−b| ≤ atol + rtol·max(|a|,|b|)`、既定 `atol = 1e-15` / `rtol = 1e-13`**。
絶対項が主、相対項は補助。この既定で K 殻・M 殻とも合格する。

### 3.3 診断値は別集計

`diag.rtail` は 1e-10 級の極小値なので、絶対差 1 ulp でも相対差が 7.5e-14 に見える。
**データセットの正しさに関わるのは F / N0 / σ** なので、`agreement_check.py` は
パスに `.diag.` を含む値を**別集計にして合否に入れない**。

## 4. ★ 予測はできない — 3 回の仮説がすべて反証された

| 立てた仮説 | 反証した測定 |
| --- | --- |
| 「LLVM が CPU 名を認識するかどうかで決まる」 (`znver5` は未知なので `generic` に落ちる) | **`-C znver4` が native と完全一致** — 名前が違っても同じ |
| 「AVX-512 が有効かどうかで決まる」 | **`-C skylake-avx512` (AVX-512 あり) が `-C skylake` (なし) と同一**で、どちらも基準と別 |
| 「共通ターゲット `-C x86-64-v3` に揃えれば機械を跨いで一致する」 | **同じ `-C x86-64-v3` を指定した 3 台が 3 通りの結果** (類 4 / 5 / 7) |

**機構**: Julia は **multi-versioned sysimage** (複数の ISA 版を同梱し実行時に選ぶ) を配布している。`-C` は
**新しくコンパイルされるコード**にしか効かず、Base などの既存コードは**ホストの CPU に応じた版**が選ばれる。
⇒ **どんなターゲット指定でも、異なるマシンをバイト一致させることはできない**。

## 5. 副産物 — アーカイブ配布の来歴

コードを tar.gz で配ると `.git` が無いため `generator_commit` が `unknown` になる (出荷 JSON に書かれる項目)。
⇒ **浅い clone (`--depth 1`) ごと固める**ことで解決した。4.1 MB、展開先で `git rev-parse --short HEAD` が
`7991cdb`、`git status --porcelain -uno` が 0 件 (= `-dirty` が付かない)、ソース指紋も一致。

## 6. 設計への反映

| | 変更前 | 変更後 |
| --- | --- | --- |
| 正常性の判定 | バイト同一 | **相対 ≤ ε (丸め誤差の範囲内)** |
| フリート参加の門 | ビット一致した CPU のみ | **廃止 — どの CPU でも参加できる** |
| データセットの保証 | 「同じ commit で再生成するとバイト一致」 | **「どの環境で再生成しても相対 ≤ ε で一致」** |
| 来歴 | (暗黙に単一マシン) | **チャネルごとに計算したホスト・CPU を記録**し、混成であることを隠さない |

**残すもの**: `RUN_SPEC.json` / `context_sha256` の fail-closed (処方・spec の取り違えは依然として致命的)、
`row_sha256` (転送破損の検出)、`tools/bitident_snapshot.jl` (**同一マシン内**のコード変更の回帰検査)。

## 7. 確定 (2026-08-21 11:40)

- **ε = 絶対 5e-16** (F(0)=1 に規格化した F(s) に対して)。K 殻の実機総当たり 10 組で最大 4.441e-16、
  M 殻で 2.220e-16。**殻による悪化は無い**。
- 判定式 `|a−b| ≤ 1e-15 + 1e-13·max(|a|,|b|)` を `tools/agreement_check.py` の既定にした。
- 実機の生ファイルは `Temari-runs/bitident_2026-08-21/` に保存 (10 実行 + ログ 11 本)。

**残る宿題** (急がない):

- L 殻での確認 (K と M が同程度なので、間の L が外れる理由は無いが未測定)
- 出荷 525 チャネル全体での確認 — **最初の分散キャンペーンの後に標本で測る**のが自然
  (`agreement_check.py <dirA> <dirB>` はディレクトリ同士を比べられる)

## 8. 使い方

```bash
# 2 つの実行結果を比べる (ディレクトリ同士でもファイル同士でも可)
python tools/agreement_check.py <dirA> <dirB> --rtol 1e-13

# 出力: 物理量の最大相対差・最大絶対差、診断値は別集計、メタデータは
#       「環境で変わる項目」と「一致すべき項目」に分けて報告
```
